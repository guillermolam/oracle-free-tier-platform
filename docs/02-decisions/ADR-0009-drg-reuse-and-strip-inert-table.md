# ADR-0009: DRG inert route table — reuse-and-strip the auto-created table

Status: Accepted

Supersedes the implementation mechanism of
[ADR-0008](ADR-0008-drg-reserved-inert-m1.md) (not its intent): ADR-0008's
decision — DRG created and attached in M1, inert until I21 — is unchanged.
Only the mechanism that makes the attachment's DRG route table "inert"
changes. Resolves `GAP-NET-004` in the threat-model corpus
(`docs/03-threat-model/model/instances/network.yaml`).

## Context

ADR-0008 Option B specified a **custom** empty DRG route table
(`platform-drg-rt-inert`) as the inert mechanism. During PR C2's real
apply, creating that table failed with an OCI per-DRG route-table-count
service-limit error: creating a DRG makes OCI auto-generate two route
tables ("Autogenerated Drg Route Table for VCN attachments" and
"...for RPC, VC, and IPSec attachments"), and this tenancy's per-DRG
route-table limit is 2 — the quota is fully consumed before any custom
table can be added. Verified live via `oci network drg-route-table list`
(2026-08-20: both auto-created tables present, `AVAILABLE`; zero
attachments exist).

PR #52 interim-gated the custom table + attachment behind
`manage_inert_drg_route_table` (default `false`) so the rest of M1's
network work could land while the mechanism was undecided — the DRG was
left genuinely unattached. This ADR is the decision that unblocks the
attachment.

## Decision

**Options considered:**

- **A.** Request a per-DRG route-table limit increase (2 → 3) and keep the
  custom inert table. Limit-increase requests are Console-only (no CLI/API
  path) and Always Free limit increases are not guaranteed; this would
  block M1's DRG attachment on an out-of-band human action with unknown
  latency, for zero functional gain.
- **B.** Reuse-and-strip: take state ownership of the auto-created
  "VCN attachments" route table (via an OpenTofu `import` block at the
  Terragrunt live layer — import blocks are root-module-only) and strip
  its default "accept all routes, no match criteria" import route
  distribution with `remove_import_trigger = true`
  (`oci_core_drg_route_table`; per the oracle/oci provider docs, flipping
  it "disables the import of route Distribution by setting
  import_drg_route_distribution_id to null"). The attachment additionally
  nulls its default export route distribution with
  `remove_export_drg_route_distribution_trigger = true`
  (`oci_core_drg_attachment`), so the path is inert in both directions.
- **C.** Keep the DRG unattached until I21 — silently violates
  SPEC-NET-002 REQ-NET-009's "MUST create ... and attach" and contradicts
  ADR-0008's still-authoritative intent.

**Decision drivers:** REQ-NET-009 requires the attachment to exist in M1;
the reuse-and-strip path consumes **zero** quota (no third table is
created), so it needs no service-limit request and no human gate; the
resulting state is identical in kind to Option B's original intent (table
present, zero route rules, no propagation); the auto-created table is
self-discovered by `drg_id` + OCI's fixed display name, so no
tenancy-specific OCID enters the module's inputs; the mechanism is
provider-supported and updatable, not a workaround.

**Decision: Option B — reuse-and-strip.** The DRG attachment becomes
unconditional again (no gating variable); `manage_inert_drg_route_table`
and the custom `inert` table resource are removed.

## Consequences

- `oci_core_drg_route_table.vcn_default` models an OCI-created object
  under state ownership. `display_name` must stay equal to OCI's fixed
  auto-generated name (the data source self-discovers by it); renaming is
  possible but would break the self-discovery filter until the data
  source is updated to match.
- A `tofu destroy` of this module's DRG resources would attempt to delete
  the OCI auto-created table. ADR-0008's Reversibility section still
  applies: destroy is safe pre-I21 (nothing depends on the DRG), and OCI
  recreates the default tables with the DRG on any subsequent create.
- The import block lives only in the live layer
  (`infrastructure/live/oci/eu-madrid-1/lab/10-network/terragrunt.hcl`'s
  `generate` block), so `examples/minimal` — which calls this module as a
  child — plans a *create* of the same-named table. That path is
  validate/plan-only in CI (never applied against real OCI); a fresh
  environment applying through the live layer imports the auto-created
  table once the DRG exists (deferred data read at apply).

## Security consequences

None beyond ADR-0008's: the stripped table holds zero route rules and no
import distribution, and the attachment exports nothing — the DRG carries
no traffic until I21. SPEC-NET-005 REQ-NET-027's verification of that
invariant is unchanged in kind; the verified object is now the reused
table (`oci_core_drg_route_table.vcn_default`) instead of a custom one.

## Operational consequences

M1 no longer depends on any OCI service-limit increase for the DRG
attachment. The M1 egress question (NAT/Service Gateway quota = 0) is a
separate concern tracked as SPIKE-NET-01 (see
`docs/00-overview/roadmap.md`); it does not interact with this decision.

## Reversibility

Fully reversible in code: re-adding a custom table is a new PR gated on a
limit increase. The state-side import is not destructive — removing the
`import` block + resource stops managing the auto-created table (a
`removed` block or `tofu state rm` releases ownership without deleting
the live object).
